# 0001 - Hybrid Fallback and Pre-Cached Golden Responses

**Date:** 2026-10-19  
**Status:** Accepted  

## Context

RasaLore AI is designed as a local-first application where **Dual-Mode Inference** relies primarily on local Google Gemma 2 weights executed via Ollama (`http://localhost:11434`). However, when evaluators, hackathon judges, or clients test the application on machines without Ollama installed or where browser Cross-Origin Resource Sharing (CORS) blocks direct localhost socket requests, the evaluation will fail immediately. Requiring a dedicated backend server or an active cloud proxy introduces infrastructure costs, secret management overhead, and deployment complexity that violates our zero-overhead, static-deploy client-side architecture.

## Decision

We decided to implement a hybrid fallback mechanism:
1. For the three curated culinary presets (*Bali Tropical Bistro*, *Warung Nusantara Autentik*, *Specialty Coffee & Heritage Sweets*), the application bundles pre-cached golden JSON responses generated by Gemma 2 with pre-translated multilingual variations. This guarantees an instant (< 500ms), 100% deterministic, zero-cost demonstration without requiring any API keys or local services.
2. For ad-hoc custom dishes entered in remote fallback mode, an optional client-side configuration drawer allows the user to supply an ephemeral Hugging Face User Access Token (`HF_TOKEN`) to invoke serverless inference directly from the browser against `google/gemma-2-2b-it`.

## Consequences

- Evaluators and judges can experience the full end-to-end functionality within 10 seconds on any device with zero setup.
- Proprietary secret tokens are never stored in repository code or centralized databases; client tokens remain in volatile memory or local session storage.
- Custom dish generation in fallback mode requires a user-provided token if serverless rate limits are encountered, which is an acceptable trade-off for maintaining a zero-backend architecture.

## Considered Options

- **Centralized Express/Node Proxy Server**: Rejected because it requires recurring hosting infrastructure, breaks air-gapped local privacy guarantees, and introduces server maintenance overhead.
- **Requiring Ollama as a Hard Prerequisite**: Rejected because remote hackathon judges and casual evaluators frequently lack the time or hardware to pull a 2GB+ model before reviewing the project.
